### Q1. 왜 MSA를 적용했나요? ⭐⭐⭐⭐⭐

**30초 버전**
> "개인 프로젝트 규모에서 MSA가 필수는 아닙니다. 하지만 실무에서는 단일 WAS 구조만 경험했기 때문에,
> 서비스가 분리되면 통신·장애 격리·배포 방식이 어떻게 달라지는지를 직접 확인하고 싶었습니다.
> 의도적으로 선택한 오버엔지니어링입니다."

**핵심 포인트**
- "공부하려고"로 끝내지 않는다. **무엇을 이해하고 싶었는지**가 핵심.
- Service Discovery, Gateway 라우팅, JWT 공유 방식, 서비스 간 REST 통신 — 이것들을 코드 레벨에서 이해하기 위해
- 실제로 겪은 문제: budget-service가 notification-service 클래스를 직접 import → 컴파일 에러 → MSA 경계 위반 확인 → NotificationClient REST 래퍼로 분리

**2분 버전**
> "실무에서 4년간 다룬 시스템은 하나의 WAS 안에서 모든 기능이 동작하는 구조였습니다.
> 그래서 서비스가 분리됐을 때 실제로 어떤 문제가 생기는지, 어떻게 해결하는지를 몸으로 경험한 적이 없었습니다.
>
> k-msa-platform을 만들면서 가장 먼저 부딪힌 문제가 있었는데, budget-service가 notification-service의
> 클래스를 직접 Java import로 사용하려 했더니 컴파일 에러가 났습니다. MSA에서 서비스 간 코드 공유가 왜
> 금지되는지를 에러 메시지로 확인한 겁니다. 결국 NotificationClient라는 REST 래퍼를 만들어 서비스 경계를
> 명확히 분리했습니다.
>
> 또 JWT를 여러 서비스가 공유하는 문제도 있었습니다. 서비스마다 같은 시크릿을 하드코딩하면 안 되니까,
> Kubernetes Secret으로 주입하고 Nginx auth_request로 인증을 위임하는 구조를 직접 구현했습니다.
>
> 이렇게 '왜 이 구조가 필요한가'를 실패를 통해 이해한 것이 이 프로젝트의 목적이었습니다."

### Q2. SI 경험이 프로덕트 서비스에서 어떻게 도움이 되나요? ⭐⭐⭐⭐⭐

**30초 버전**
> "운영 환경에서 실제로 터진 장애를 로그부터 네트워크까지 직접 추적한 경험이 있습니다.
> 이 경험은 서비스 회사에서도 동일하게 쓰입니다. 장애는 코드 문제만이 아니기 때문입니다."

**핵심 포인트**
- SI는 납기·스펙 기반, 서비스는 운영·개선 기반 — 이 차이를 먼저 인정
- 그러나 '운영'과 '장애 대응' 자체는 SI에서 오히려 더 많이 경험
- Apache, WAS, DB, HTTP 전문, 인증서, 네트워크 — 이 레이어를 실제로 열어본 경험

**2분 버전**
> "SI와 프로덕트는 일하는 방식이 다릅니다. SI는 납기 안에 요구사항을 구현하는 것이 목표고,
> 프로덕트는 서비스를 출시한 이후에도 데이터를 기반으로 계속 개선하는 것이 목표라고 생각합니다.
>
> 그 차이는 명확하게 인식하고 있습니다. 하지만 '운영'이라는 관점에서는 오히려 SI가 더 다양한 환경의
> 장애를 경험합니다. 프로젝트마다 다른 인프라, 다른 외부 기관, 다른 인증 방식이 있었고 거기서 터지는
> 문제들을 직접 추적했습니다.
>
> 예를 들어 외부 전자보증 연계에서 요청은 나가는데 응답이 안 오는 문제가 있었습니다. HTTP 전문을 먼저 확인해
> 내부가 정상임을 입증하고, WAS → DB → Apache 순으로 범위를 좁힌 뒤 네트워크까지 확장해서 운영 서버
> 송신 IP가 바뀌어 상대 기관 허용 목록에서 빠진 것을 원인으로 찾았습니다. 타임아웃이 0.05초 응답으로
> 돌아왔습니다.
>
> 이 경험은 서비스 회사에서도 그대로 씁니다. 장애는 코드만으로는 설명이 안 되는 경우가 많고,
> 그럴 때 어디부터 어떻게 범위를 좁히는지를 아는 것이 실질적인 차이를 만든다고 생각합니다."

### Q3. 왜 네이버웹툰인가?

**30초 버전**
> "전 세계 사용자가 매일 이용하는 서비스를 안정적으로 운영하면서도 지속적으로 기능을 개선하는
> 조직에서, 제가 체득한 운영 경험과 근거 기반 문제 해결 방식을 실서비스 규모에서 검증하고 싶습니다."

**핵심 포인트**
- "웹툰을 좋아해서"로 시작하지 않는다
- 기술적 도전 관점 — 글로벌 콘텐츠 플랫폼의 CDN, 이미지 처리, 트래픽 특성
- 내 운영 경험 + 프로덕트 서비스 학습을 결합하기에 맞는 조직

**2분 버전**
> "네이버웹툰은 특정 기능보다 서비스 안정성이 핵심인 조직이라고 생각합니다.
> 독자가 회차를 열었을 때 이미지가 늦게 뜨거나 오류가 나면 바로 이탈합니다.
> 그래서 트래픽 처리, CDN 운영, 장애 감지와 복구가 기능 개발만큼 중요한 조직입니다.
>
> 저는 4년간 SI에서 운영 환경 장애를 직접 추적하고 해결하는 경험을 쌓았는데,
> 이 경험을 실서비스 규모에서 써보는 것이 지금 제 성장 목표와 정확히 맞닿아 있습니다.
>
> 동시에 부족한 부분도 알고 있습니다. 수천만 사용자 규모의 서비스를 직접 운영해본 경험은 없습니다.
> 그래서 개인 프로젝트에서 관측성 환경을 직접 구성하고, SLO 기준을 정의해 검증하는 작업을 하며
> 그 감각을 익히고 있습니다. 네이버웹툰에서 더 큰 규모의 문제를 경험하고 싶습니다."

### Q4. 가장 어려웠던 장애 경험은?

**30초 버전**
> "외부 전자보증 기관 연계에서 요청은 정상 전송됐지만 응답이 오지 않는 상황이었습니다.
> 코드는 문제가 없었고 HTTP 전문과 로그를 단계적으로 추적해 운영 서버 IP 변경이 원인임을 찾았습니다."

**핵심 포인트**
- 코드를 먼저 의심하지 않는다 — 레이어별 추적이 핵심
- 내부 정상 입증 → 외부 원인 확정 순서
- HTTP 전문 → WAS → DB → Apache → 네트워크 → 상대 기관 허용 IP

**2분 버전**
> "외부 전자보증 기관과 연계하는 배치 처리에서 요청은 나가는데 응답이 오지 않는 문제가 있었습니다.
> 오류 메시지가 없어서 처음에는 어디서 멈추는지 알 수 없었습니다.
>
> 먼저 HTTP 요청·응답 전문을 확인했습니다. 우리 측에서는 정상 요청이 전송됐습니다.
> 다음으로 WAS 로그, DB 로그, Apache 로그를 순서대로 확인해 내부 처리가 모두 정상임을 입증했습니다.
>
> 내부가 정상이라면 문제는 외부에 있습니다. 네트워크 정책을 확인했고, 그 결과 최근 운영 서버 배포 과정에서
> 송신 IP가 변경됐는데 상대 기관 허용 IP 목록이 갱신되지 않은 것을 발견했습니다.
>
> 상대 기관에 IP 변경을 요청하고 허용 목록을 업데이트한 뒤, 타임아웃이 발생하던 요청이 0.05초 정상 응답으로
> 복구됐습니다.
>
> 이 경험에서 배운 것은, 추측으로 범위를 좁히면 안 된다는 겁니다. 레이어별로 내부를 먼저 무결함으로
> 입증하면 남은 범위가 자연스럽게 좁혀집니다."

### Q5. 로그는 어떻게 봤나요?

**30초 버전**
> "Apache → WAS → DB 순으로 봤습니다. 요청이 어느 레이어까지 도달했는지를 먼저 확인하고,
> 도달한 레이어에서 무슨 처리가 됐는지를 확인하는 방식입니다."

**핵심 포인트**
- 로그를 보는 순서가 있다 — 외부 → 내부 방향 혹은 진입점 → 처리 방향
- 각 레이어에서 확인하는 것이 다르다
- HTTP 전문은 코드와 독립적으로 실제 요청/응답 내용을 확인

**2분 버전**
> "문제 유형에 따라 다르지만 기본 순서는 Apache access log → WAS 로그 → DB 쿼리 로그입니다.
>
> Apache access log에서는 요청이 서버에 도달했는지, HTTP 상태코드가 무엇인지를 먼저 봅니다.
> 여기서 4xx/5xx가 나오면 WAS 로그를 보고 어디서 예외가 발생했는지 확인합니다.
> 예외가 없는데 응답이 늦거나 없으면 DB 쿼리 로그를 봐서 슬로우 쿼리나 락 대기가 있는지 확인합니다.
>
> 외부 연계 문제는 HTTP 전문을 별도로 캡처합니다. 애플리케이션 로그와 실제 HTTP 전문이 다른 경우가
> 있어서, 실제 요청/응답 내용을 직접 확인하는 게 중요합니다. 특히 인증서나 인코딩 문제는 전문을
> 봐야 드러납니다."

### Q6. Gateway는 왜 넣었나요?

**30초 버전**
> "서비스가 여러 개일 때 클라이언트가 각 서비스의 주소를 알아야 하면 관리가 복잡해집니다.
> Gateway를 단일 진입점으로 두고 인증도 거기서 위임 처리하면, 각 서비스는 인증 로직 없이
> 자기 도메인에만 집중할 수 있습니다."

**핵심 포인트**
- 단일 진입점 → 클라이언트 단순화
- Nginx auth_request → auth-service /auth/verify → 인증 중앙화
- X-User-Id 헤더 주입 → 각 서비스는 인증 검증 없이 사용자 식별 가능
- 서비스 추가/변경 시 클라이언트 변경 없음

**2분 버전**
> "서비스가 auth, budget, blog, notification 4개로 나뉘어 있는데, 클라이언트가 각각의 포트와 주소를
> 알아야 하면 서비스가 추가되거나 주소가 바뀔 때마다 클라이언트도 변경해야 합니다.
>
> Gateway를 단일 진입점으로 두면 클라이언트는 Gateway 주소 하나만 알면 됩니다.
>
> 인증도 Gateway에서 처리했습니다. Nginx의 auth_request 지시어로 모든 요청을 auth-service의
> /auth/verify로 먼저 보내고, 검증이 통과하면 X-User-Id 헤더를 추가해서 downstream 서비스로
> 전달합니다. 각 서비스는 JWT를 직접 검증하지 않고 헤더만 읽으면 됩니다.
>
> 이 구조 덕분에 새 서비스를 추가할 때 인증 로직을 반복 구현하지 않아도 됩니다."

### Q7. Kubernetes를 왜 사용했나요? Docker Compose와 차이는?

**30초 버전**
> "Docker Compose는 여러 컨테이너를 한 번에 띄우는 도구입니다. Kubernetes는 거기서 한 단계 더 나아가
> 장애가 나면 자동으로 재시작하고, 트래픽이 늘면 자동으로 복제본을 늘리는 선언적 운영 환경입니다."

**핵심 포인트**
- Docker Compose: 로컬 개발·테스트에 적합, 오토스케일 없음, Self-healing 없음
- Kubernetes: HPA(Horizontal Pod Autoscaler), Self-healing, Rolling update, K8s Secret 관리
- JWT Secret을 K8s Secret으로 관리 → 하드코딩 없이 환경변수 주입

**2분 버전**
> "처음엔 Docker Compose로 충분했습니다. 로컬에서 8개 컨테이너를 한 번에 띄우는 건 Compose가 간단합니다.
>
> Kubernetes를 추가한 이유는 두 가지입니다. 첫째는 오토스케일입니다. Compose는 컨테이너를 고정 개수로만
> 운영합니다. 트래픽이 늘어도 자동으로 복제본이 늘지 않습니다. HPA를 써보려면 Kubernetes가 필요했습니다.
>
> 둘째는 Secret 관리입니다. JWT 시크릿 키를 4개 서비스가 공유해야 하는데, 하드코딩하거나 환경변수 파일을
> 각 서비스에 복사하면 관리가 안 됩니다. K8s Secret 하나를 여러 서비스에 envFrom으로 주입하면
> 한 곳에서 관리할 수 있습니다.
>
> 그리고 컨테이너가 죽으면 자동 재시작(Self-healing), 배포할 때 Rolling update로 다운타임 없이 교체 —
> 이 부분들을 실제로 구성해보고 싶었습니다."

### Q8. Prometheus/Grafana는 왜 사용했나요?

**30초 버전**
> "문제가 생겼을 때 '어디서 생겼는지'를 찾으려면 수치로 된 기준이 있어야 합니다.
> Prometheus로 메트릭을 수집하고 Grafana로 시각화하면, 이상 시점과 이상 서비스를 빠르게 좁힐 수 있습니다."

**핵심 포인트**
- 단순 모니터링이 아니라 관측성(Observability)
- Pull 방식 — 서비스에 에이전트 심지 않아도 scrape endpoint만 노출하면 됨
- SLO 위반 시 알림 설정 가능
- 운영 중 어느 서비스가 병목인지 수치로 확인

**2분 버전**
> "로그만으로는 '지금 서비스가 얼마나 느린가'를 알기 어렵습니다. 에러 로그는 이미 터진 후에 보이고,
> 느려지고 있는 중간 상태는 로그에 안 잡힙니다.
>
> Prometheus는 서비스에서 scrape endpoint(/actuator/prometheus)를 노출하면 주기적으로 메트릭을 긁어갑니다.
> 요청 수, 응답시간 분포, 에러율이 시계열로 쌓입니다.
>
> 이 데이터를 Grafana에서 SLO 기준선과 함께 보면, 어느 시점에 p95가 올라가고 어느 서비스에서 에러율이
> 증가했는지를 시각적으로 확인할 수 있습니다.
>
> 또 Prometheus는 Pull 방식이라 서비스 코드에 에이전트를 심지 않아도 됩니다. 서비스가 추가되면
> scrape config에 target만 추가하면 됩니다. MSA 환경에서 서비스가 늘어날수록 이 방식이 관리하기 쉽습니다."

### Q9. SLO를 왜 만들었나요?

**30초 버전**
> "'빠르다'는 주관적입니다. SLO는 판단 기준입니다.
> 기준이 있어야 '지금 성능이 괜찮은가'를 수치로 말할 수 있고, 변경 후 회귀가 생겼는지도 감지할 수 있습니다."

**핵심 포인트**
- 성능은 상대적 — 기준이 없으면 "빨라졌다/느려졌다"를 말할 수 없다
- p95 < 500ms, 에러율 < 1% — k6 threshold로 자동 검증
- 기준 위반 시 k6 테스트가 실패 상태로 표시됨 → CI에 연결 가능

**2분 버전**
> "부하 테스트를 처음 설계할 때 TPS가 높게 나오면 좋은 건지, 얼마나 나와야 좋은 건지 기준이 없었습니다.
>
> SLO를 먼저 정하면 판단이 달라집니다. p95 < 500ms, 에러율 < 1%라는 기준을 세우면,
> 지금 테스트 결과가 이 기준을 통과하는지 실패하는지를 수치로 말할 수 있습니다.
>
> k6에 threshold로 등록해두면 기준을 넘지 못할 경우 테스트 자체가 실패 상태로 리포트됩니다.
> 나중에 CI/CD에 연결하면 성능 회귀를 자동으로 감지할 수 있는 구조가 됩니다.
>
> 결국 SLO는 '성능이 좋다'는 주장을 증거로 바꾸는 도구입니다.
> 코드가 바뀌었을 때 이전보다 나빠졌는지를 기준 없이 판단하기 어렵고,
> 그 기준을 팀이 공유하면 같은 기준으로 커뮤니케이션할 수 있습니다."

### Q10. 앞으로 가장 배우고 싶은 것은?

**30초 버전**
> "대용량 환경에서의 캐시 전략과 메시징 처리입니다.
> 개인 프로젝트에서는 Redis나 Kafka를 도입할 필요가 없었지만, 실서비스에서는 이 두 가지가
> 성능과 안정성을 가르는 핵심이라고 생각합니다."

**핵심 포인트**
- Redis: 캐시 전략(TTL, eviction policy, cache stampede 방지) — 조회 집중 서비스에서 필수
- Kafka: 서비스 간 비동기 이벤트 — MSA에서 트랜잭션 정합성 없이 느슨한 결합 가능
- 운영 자동화: GitOps(ArgoCD), 배포 파이프라인 고도화
- 장기적으로: 실서비스 분산 트레이싱(Zipkin/Jaeger), DB 성능 튜닝

**2분 버전**
> "가장 배우고 싶은 건 캐시와 메시징입니다.
>
> Redis는 개인 프로젝트 규모에서는 도입할 근거가 없었습니다. 하지만 웹툰처럼 조회가 압도적으로 많은
> 서비스에서는 DB에 매번 직접 접근하면 한계가 옵니다. TTL 설정, eviction policy, cache stampede 방지 —
> 이런 캐시 전략을 실제로 경험해보고 싶습니다.
>
> Kafka는 MSA에서 서비스 간 결합도를 낮추는 핵심이라고 생각합니다. 현재 프로젝트에서는
> REST 동기 호출로 서비스 간 통신을 구현했는데, 이벤트 기반으로 바꾸면 한 서비스가 느려져도
> 다른 서비스에 영향이 덜 전파됩니다. 비동기 메시징을 실서비스 규모에서 다뤄보는 것이 목표입니다.
>
> 그리고 운영 자동화 — GitOps 방식으로 배포 파이프라인을 구성하고, ArgoCD 같은 도구로
> 선언적 배포를 경험해보고 싶습니다."

### Q11. SI와 서비스 회사의 차이가 뭐라고 생각하세요? (보너스 ⭐⭐⭐)

**30초 버전**
> "SI는 요구사항을 일정 안에 정확히 구현하는 것이 목표입니다.
> 서비스는 기능을 출시한 이후에도 데이터를 기반으로 지속적으로 개선하고 운영하는 것이 목표입니다.
> 그 차이를 알기 때문에 저는 개인 프로젝트에서 운영 관점과 서비스 구조를 직접 보완해 왔습니다."

**핵심 포인트**
- 답 자체는 짧게 — 길게 말하면 오히려 이상하다
- "그 차이를 알고 있고, 그래서 준비했다"는 메시지로 마무리
- SI 경험을 방어적으로 설명하지 않는다

**전체 답변**
> "SI에서는 요구사항을 일정 안에 정확히 구현하는 것이 가장 중요했습니다.
> 반면 프로덕트는 기능을 출시한 이후에도 데이터를 기반으로 지속적으로 개선하고 운영하는 것이 중요하다고
> 생각합니다.
>
> 그래서 저는 실무에서 부족했던 운영 관점과 서비스 구조를 개인 프로젝트를 통해 계속 보완해 왔습니다.
>
> 다만 SI에서도 운영은 했습니다. 여러 프로젝트의 운영 환경 장애를 직접 추적하고 해결했고,
> 그 경험은 서비스 회사에서도 동일하게 쓰인다고 생각합니다."
